Lesson 1Introduction to ASE

What is ASE?

ASE is a Python library for setting up, manipulating, running, visualizing, and analyzing atomistic simulations. It doesn't perform the core calculations itself (like integrating equations of motion or calculating forces for complex potentials) but acts as a powerful interface or “glue” connecting various external simulation codes (like LAMMPS, GPAW, VASP, Quantum Espresso) and internal calculators (like the Lennard-Jones calculator we'll use).

Key features

Atoms object

A central object representing a collection of atoms with positions, momenta, cell dimensions, boundary conditions, etc.

Calculators

Objects attached to Atoms that compute energy and forces (e.g., LJ potential, EMT potential, interfaces to DFT codes or complex force fields via OpenMM/LAMMPS).

Dynamics / optimization

Modules for running MD simulations (NVE, NVT, NPT using various integrators/thermostats) or performing structure optimization.

Input / output

Reading and writing various file formats common in atomistic simulations.

Analysis tools

Built-in functions for common analysis tasks (e.g., RDF).

Building tools

Functions for creating common structures (surfaces, bulk crystals, nanotubes, etc.).

Installation

If you haven't installed ASE yet, you can typically do so via pip:

pip install ase

Or conda:

conda install -c conda-forge ase

Basic ASE objects

  • ase.Atoms: Stores the state of the system (positions, numbers, cell, pbc, calculator, momenta).
  • ase.calculators: Contains modules for different ways to calculate energy and forces. We'll use ase.calculators.lj.LennardJones.

Lesson 2Setting Up the LJ Fluid

We'll simulate Argon (Ar), a noble gas often modeled using the Lennard-Jones potential. The LJ potential is:

$$ V_{LJ}(r) = 4\epsilon \left[ \left(\frac{\sigma}{r}\right)^{12} - \left(\frac{\sigma}{r}\right)^{6} \right] $$

For Argon, typical parameters are:

  • $\sigma \approx 3.405$ Å (Angstroms)
  • $\epsilon \approx 0.0103$ eV (electron Volts) or $119.8$ K $\times k_B$

ASE uses specific units internally (eV for energy, Å for length).

Steps

  1. Create an initial configuration of Ar atoms (e.g., start from a face-centered cubic (fcc) lattice).
  2. Define the simulation box and apply Periodic Boundary Conditions (PBC).
  3. Set up the Lennard-Jones calculator with the appropriate parameters.
  4. Assign initial velocities corresponding to a desired temperature.
💡 Deep dive: reduced LJ units (what the browser engine uses)

Because the LJ potential has only two parameters, every LJ system can be written in reduced units with $\sigma = \epsilon = m = k_B = 1$. Results for argon are then just a rescaling. The JavaScript engine on this page works in reduced units and converts back to argon units (Å, eV, K, fs) for display:

Create initial configuration

We can use ase.build.bulk to create a unit cell and then repeat it to get a larger system. We choose a lattice constant a appropriate for the desired density. The density affects the phase (solid, liquid, gas). Let's aim for a liquid-like density.

Build a 5×5×5 fcc argon box (500 atoms) and report its density

Set up the LJ calculator

Attach the LennardJones calculator to the Atoms object. ASE's LJ calculator uses $\sigma$ and $\epsilon$. Here we also set a cutoff radius rc = 3σ: pairs farther apart than $r_c$ are ignored, and ASE shifts the pair energy so that it is exactly zero at $r_c$ (no jump in energy when a pair crosses the cutoff — see Module 3).

Attach the LennardJones calculator and minimise with BFGS
# Set the calculator
atoms.calc = LennardJones(sigma=sigma_Ar, epsilon=epsilon_Ar, rc=sigma_Ar * 3.0) # rc is cutoff radius

# Check initial energy and forces (should be non-zero due to initial lattice)
initial_potential_energy = atoms.get_potential_energy()
initial_forces = atoms.get_forces()
print(f"Initial Potential Energy: {initial_potential_energy:.4f} eV")
# print(f"Max initial force component: {np.max(np.abs(initial_forces)):.4f} eV/A")

# Optional: Minimize energy to get a more stable starting point (removes initial forces)
print("Minimizing initial structure...")
optimizer = BFGS(atoms, logfile='minimization.log')
optimizer.run(fmax=0.01) # Run until max force component is below 0.01 eV/A
minimized_potential_energy = atoms.get_potential_energy()
print(f"Minimized Potential Energy: {minimized_potential_energy:.4f} eV")
write('minimized_structure.xyz', atoms)

Minimizing initial structure...
Minimized Potential Energy: -34.9023 eV
Why did the minimiser change nothing?

The initial and minimized energies are identical (−34.9023 eV). In a perfect fcc lattice every atom sits at a centre of symmetry: each neighbour pulling one way is matched by a neighbour pulling the opposite way, so the net force on every atom is zero. BFGS finds the largest force already below fmax = 0.01 eV/Å and stops at step 0. Minimisation matters when the starting structure has clashes — atoms placed too close together, as happens with random placement, solvated molecules, or structures built by hand. The lab below lets you create such clashes and watch a minimiser remove them.

The 500-atom fcc box with a = 5.7 Å has a potential energy of −34.9023 eV both before and after BFGS(...).run(fmax=0.01). Why?

  1. BFGS is not able to minimise Lennard-Jones systems.
  2. The cutoff rc = 3σ removes all forces between atoms.
  3. By symmetry, the forces on every atom of a perfect lattice cancel, so the convergence criterion is met before any step is taken.
  4. The lattice constant 5.7 Å is exactly the energy minimum of the crystal.
Every atom in a perfect fcc lattice is a centre of inversion, so its neighbours' forces cancel pairwise. That makes the structure a stationary point (zero force), even though it is not the lowest-energy lattice: the box builder above shows the energy is lower near a ≈ 5.27 Å.

Lesson 3Running NVT with ASE

Now we set up the Molecular Dynamics simulation run itself. We'll use the Langevin thermostat to maintain the target temperature (NVT ensemble).

Steps

  1. Choose simulation parameters (time step, total steps).
  2. Create a Langevin dynamics object, linking the Atoms object, time step, temperature, and friction coefficient.
  3. Define how to log data or save the trajectory during the run.
  4. Run the simulation using the dyn.run() method.

Notice how much of the code below is bookkeeping (logging, trajectory files, error handling): the physics is a single line, dyn.run(n_steps). The friction 0.01 / units.fs means velocities forget their direction on a time scale of $1/\gamma = 100$ fs, so the thermostat pulls the temperature to 90 K quickly.

Langevin NVT run: 2000 steps of 5 fs with logging and a trajectory file
# Simulation parameters
time_step_fs = 5.0 # femtoseconds
time_step = time_step_fs * units.fs
# Define picoseconds numerically based on femtoseconds
# This 'ps' variable holds the value of 1 picosecond in ASE's internal time units
ps = 1000.0 * units.fs
total_simulation_time_ps = 10.0 # picoseconds
total_simulation_time = total_simulation_time_ps * ps # Total time in ASE units
n_steps = int(total_simulation_time / time_step)
log_interval = 200 # Print status less often
traj_interval = 1000 # Save trajectory frame less often
traj_filename = 'lj_argon_nvt.traj'

print(f"Simulation time step: {time_step_fs:.1f} fs ({time_step / units.fs:.3f} ASE time units)")
print(f"1 Picosecond equals: {ps:.3f} ASE time units")
print(f"Total simulation time: {total_simulation_time_ps:.1f} ps ({total_simulation_time:.3f} ASE time units)")
print(f"Number of steps: {n_steps}")

# Set up Langevin dynamics
friction_coeff = 0.01 / units.fs
dyn = Langevin(atoms, timestep=time_step, temperature_K=target_temperature_K, friction=friction_coeff)

# Function to print progress
def print_status(a=atoms):
    """Function called by the dynamics to print status."""
    step = dyn.get_number_of_steps()
    if step % log_interval == 0: # Print only at log_interval
        epot = a.get_potential_energy() / len(a)
        ekin = a.get_kinetic_energy() / len(a)
        # Ensure temperature calculation is safe (avoid division by zero if ekin is zero)
        temp = ekin / (1.5 * units.kB) if ekin > 1e-9 else 0.0
        # Calculate current time in picoseconds using the 'ps' variable defined earlier
        current_time_ps = (step * time_step) / ps
        print(f'Step: {step:6d}, Time: {current_time_ps:6.2f} ps, '
              f'Epot/N: {epot:.4f} eV, Ekin/N: {ekin:.4f} eV, Temp: {temp:.1f} K')

# Attach status printing
# The dyn object will call print_status() at each step internally.
# The check for log_interval is handled inside print_status.
dyn.attach(print_status, interval=1) # Attach to be called every step

# Set up trajectory saving
# Check if file exists, delete if you want to overwrite cleanly
if os.path.exists(traj_filename):

        os.remove(traj_filename)
        print(f"Removed existing trajectory file: {traj_filename}")
    except OSError as e:
        print(f"Error removing existing trajectory file {traj_filename}: {e}")
        # Decide if you want to exit or continue
        # exit() or pass

# Use a try-finally block to ensure the trajectory file is opened and closed properly
trajectory = None # Initialize trajectory to None
try:
    trajectory = Trajectory(traj_filename, 'w', atoms)
    # Attach trajectory writing with the specified interval
    dyn.attach(trajectory.write, interval=traj_interval)

    print(f"Starting NVT simulation for {n_steps} steps...")
    print(f"Target Temperature: {target_temperature_K:.1f} K")

In the NVT log, the temperature wanders between about 84 K and 96 K instead of staying at exactly 90 K. What does this mean?

  1. The thermostat is broken; a correct Langevin thermostat holds the temperature fixed at every step.
  2. This is expected: the thermostat fixes the average temperature, and the instantaneous kinetic temperature of a finite system fluctuates.
  3. The time step is too large, so energy is not conserved.
In the canonical (NVT) ensemble the kinetic energy fluctuates. For $N$ atoms the relative size of the temperature fluctuations is about $\sqrt{2/(3N)}$, which is 3.7% (≈ 3 K) for 500 atoms — just what the log shows. Compare 256 and 500 atoms in the phase explorer below: the smaller system fluctuates more.

To observe different phases (solid, liquid, gas), you would typically run similar simulations but change the target_temperature_K (and potentially the initial density/lattice constant).

💨 Gas

Higher temperature (e.g., 300 K) and lower density (larger lattice_constant or fewer atoms in the box).

Exercise 1 — Time step and friction

In the NVT lab above, press Reset, then change one parameter at a time and run the full 10 ps:

  1. Increase the time step from 5 fs to 20, 40, 80 and finally 100 fs. When does the average temperature start to deviate from the 90 K target, and when does the simulation blow up?
  2. Go back to 5 fs and change the friction from 0.01 fs⁻¹ to 0.001 fs⁻¹ and to 0.05 fs⁻¹. How does the size of the temperature fluctuations change, and how quickly does the temperature settle after you move the target slider?
What you should see

Time step. Up to about 20 fs the run looks fine. At 40–80 fs the measured temperature settles a few kelvin below the target: the discretisation error now distorts the sampled distribution even though nothing explodes. Near 100 fs ($\Delta t^* \approx 0.05$) atoms move so far in one step that two of them land almost on top of each other, the $r^{-12}$ repulsion produces an enormous force, and the run blows up within a few dozen steps. The 5 fs used in this module is a cautious, safe choice.

Friction. The temperature fluctuations are a property of the ensemble, so they stay roughly the same size; what changes is how fast the thermostat reacts and how strongly it perturbs the dynamics. With heavy friction (0.05 fs⁻¹) atoms are constantly kicked by the bath and diffuse more slowly; with light friction (0.001 fs⁻¹) the dynamics is close to Newtonian (NVE) between gentle corrections, and the temperature takes picoseconds rather than a few hundred femtoseconds to follow a new target. For static properties such as $g(r)$ the choice hardly matters; for dynamical properties (diffusion, viscosity) use a weak thermostat.

Lesson 4Analyzing the LJ Fluid

After the simulation, we analyze the results stored in the log files and trajectory.

Thermodynamic properties

Temperature, potential energy, kinetic energy, and total energy were printed during the run. We can also extract them from the saved trajectory or log files for plotting time series or calculating averages. Pressure can also be calculated (related to forces and kinetic energy via the virial theorem), especially important for NPT simulations.

Structural properties

  • Density: Calculated from the number of atoms, mass, and box volume. Should remain constant in NVT.
  • Radial Distribution Function (RDF), $g(r)$: This is a crucial function describing the structure of fluids and solids. $g(r)$ measures the probability of finding another particle at a distance $r$ from a reference particle, relative to the probability expected for a uniform random distribution (ideal gas).
$$ g(r) = \frac{\langle n(r, r+\Delta r)\rangle}{\rho \, 4\pi r^2 \Delta r} $$

where $\langle n(r, r+\Delta r)\rangle$ is the average number of neighbours in a thin shell around a reference atom and $\rho = N/V$. An ideal gas has $g(r) = 1$ everywhere.

💨 Gases

$g(r)$ quickly approaches 1 for $r > \sigma$, indicating little structure.

💧 Liquids

Show a strong peak around $r \approx \sigma$ (first solvation shell), followed by damped oscillations approaching 1, indicating short-range order.

🧊 Solids

Show sharp, distinct peaks corresponding to crystallographic neighbor distances, indicating long-range order.

Calculating RDF using ASE

ASE provides tools to calculate the RDF from an Atoms object or a trajectory.

Computing the radial distribution function

Let's calculate the RDF for the final state of our simulation. For a proper analysis, one would typically average the RDF over several frames from the production phase of the trajectory.

Compute and plot g(r) of the final state with get_rdf
# --- RDF Calculation ---
# We need the final Atoms object from the simulation
# The 'atoms' object should hold the final state after dyn.run()

# Parameters for RDF calculation
rmax = min(atoms.cell.lengths()) / 2.0 - 0.1 # Maximum distance (up to half the box size)
nbins = 100 # Number of bins for the RDF histogram

print(f"Calculating RDF up to rmax = {rmax:.2f} A with {nbins} bins...")

try:
    # get_rdf returns rdf values and corresponding bin centers (r)
    rdf, r = get_rdf(atoms, rmax, nbins) # Use the final 'atoms' state

    # Plot the RDF
    plt.figure(figsize=(8, 5))
    plt.plot(r, rdf)

    print("- Expect a strong peak near sigma (~3.4 A) representing the first neighbor shell.")

The RDF code sets rmax = min(atoms.cell.lengths()) / 2.0 - 0.1. Why stop $g(r)$ just short of half the box length?

  1. With periodic boundaries and the minimum image convention, separations beyond half the box are not uniquely defined — beyond $L/2$ a pair's nearest image distance can no longer be counted correctly.
  2. Because $g(r)$ is always exactly 1 beyond half the box length.
  3. To make the calculation faster; any larger value would give the same curve.
The minimum image of a neighbour is never farther than $L/2$ along each axis, so shells with $r > L/2$ are only partly sampled and $g(r)$ would be biased low there. The same reasoning is why the cutoff $r_c$ must also be smaller than $L/2$.
🔎 A closer look: liquid, or hot crystal?

The $g(r)$ above looks like a textbook liquid, and 90 K is in the liquid range of argon. But this state point ($T^* \approx 0.75$, $\rho^* \approx 0.85$) lies right on the freezing line, and the run started from a perfect fcc crystal. Ten picoseconds are not enough to melt it:

  • Energy. The rise of Epot/N from −0.0698 eV to about −0.061 eV in the first picosecond is mostly equipartition, not melting: the kinetic energy given to the atoms is shared with the potential energy of their vibrations (a harmonic crystal gains $\tfrac{3}{2}k_BT \approx 0.0116$ eV per atom). A genuinely molten sample at the same $T$ and $\rho$ sits higher, near −0.058 eV.
  • Dynamics. The mean-squared displacement (MSD) in the NVT lab levels off near 1 Å²: atoms rattle in strongly distorted cages but do not diffuse. In the melted liquid the MSD keeps growing, about 0.2 Å² per ps with this thermostat.
  • Structure. At 90 K the thermal vibrations are large enough to smear the crystal peaks into liquid-like ones. The first peaks of the two are almost identical (≈ 3 near 3.75 Å). What gives the crystal away is further out: a taller second peak (≈ 1.45 vs ≈ 1.3) and a sharper third peak at 10.6 Å — the large fcc shell at $a\sqrt{7/2}$ with 48 neighbours — where the liquid has only a weak, broad bump near 10.1 Å.

The lesson is general: one $g(r)$ snapshot from a short run can mislead. Check that energies have reached a plateau, look at dynamics (MSD or diffusion), and, when a state is close to a phase boundary, prepare it from both sides (here: melt at high temperature first, then cool). The phase explorer below has a start from a melt option to do exactly that.

Strong but broad neighbour shells that decay to 1 signal short-range order without long-range order, and wandering atoms mean the system flows — a liquid. A solid has sharp peaks that persist across the whole box and atoms that only vibrate; a dilute gas has a single weak peak and $g(r) \approx 1$ beyond about $1.5\sigma$.

Exercise 3 — Average the RDF over the trajectory

The code above computes $g(r)$ from the final frame only. Write a short Python snippet that reads lj_argon_nvt.traj, computes get_rdf for every saved frame after the starting lattice, and averages them. Why does traj_interval = 1000 make this average poor, and what would you change?

One possible solution 
from ase.io import read
from ase.geometry.analysis import get_rdf

frames = read('lj_argon_nvt.traj', index=':')   # every saved frame
production = frames[1:]                          # skip the initial fcc lattice

rdfs = []
for frame in production:
    g, r = get_rdf(frame, rmax, nbins)
    rdfs.append(g)
rdf_avg = np.mean(rdfs, axis=0)

plt.plot(r, rdf_avg, label=f"average of {len(rdfs)} frames")
plt.axhline(1.0, color='grey', linestyle='--', linewidth=1)
plt.xlabel("Distance r (Å)")
plt.ylabel("g(r)")
plt.legend()
plt.show()

With a frame saved only every 1000 steps, a 2000-step run leaves just a couple of production frames, so the average is barely better than a single snapshot. Save frames more often (e.g. traj_interval = 50) and discard the first couple of picoseconds while the lattice melts. The “time-average over the run” curve in the RDF lab does exactly this (one frame every 20 steps after 2 ps), and it is visibly smoother than the final-frame curve.
